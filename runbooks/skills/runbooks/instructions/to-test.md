# Runbook to test script: instructions

You write or adopt the test script of the runbook your brief names. The parameters are in `${CLAUDE_PLUGIN_ROOT}/commands/to-test.md`.

You cannot ask the user. Where this file says to ask (`AskUserQuestion`, "ask the user", a diff approval), stop with `status: question` as `agents.md` says. Where it says to say something and stop, put the message in `summary:` and report `status: done`. Commit nothing: the main session commits after it prints your summary.

Read first: `${CLAUDE_PLUGIN_ROOT}/skills/runbooks/references/format.md` ("Scripts of api runbooks"), and for a `ui` runbook `${CLAUDE_PLUGIN_ROOT}/skills/runbooks/references/upstream.md` ("Fixtures", "Control routes", "Scripts").

The runbook is the source of truth. A script changes to match the runbook; the runbook changes only when the user says it is the one that is wrong, and then through `/runbooks:update`.

`run` also reaches this file for an `api` runbook whose script is missing or out of sync, or whose failure looks like a script mistake. Two cases. When `run` launched you for it (escalation), your brief says what to skip. When a `run` sub-agent follows this file itself (`Forced model: yes`), skip item 6 (the run is that run) and item 9. Do not end with a report: list the script in the run's `files:` and go on with the run. In both cases the run commits the script, so item 9 only lists the script in `files:` and names its path and the `scripts:` change in `summary:`.

With role tracking on (`roles.enabled` in the config), also read the Roles part of "Scripts of api runbooks" in `format.md`, and for a runbook with cases the "Contexts and cases" section. The role rules below apply only then, and the case rules only to a runbook with cases. A script written before tracking was on has no role in its test names, so it no longer matches its runbook. Rewrite it as item 5 says and show the renamed tests in the mapping of item 3.

1. **Target.** A `placeholder` has no steps; stop and offer `/runbooks:create --from placeholder <id>`. Read `tests.<surface>` for the runbook's `surface`. When it is missing, stop and offer `/runbooks:setup` to pick a test library for that surface. When `tests.<surface>.root` is set and the folder does not exist, stop: for `tests.ui.root` outside the project, say that the UI tests repository is cloned at that path relative to this project (`${CLAUDE_PLUGIN_ROOT}/docs/adr/0007-ui-tests-may-live-in-another-repo.md`). A new script's default path and every path in `scripts` start with `tests.<surface>.root` when it is set, relative to the project root.
2. **Find existing tests.** A file in `scripts` that already has tests named with this runbook's step ids is an adopted script: it is the target, edited, never regenerated from scratch. A file in `scripts` with no such test is a candidate (from `/runbooks:map`) and goes to item 3. When `scripts` has no adopted script, also search `tests.<surface>.dir` (in `tests.<surface>.root`) for tests of the same flow: the runbook's `covers.entries` (paths and methods of its endpoints, routes of its pages), the code those entries live in, and the capability and flow words. Keep the files whose tests exercise what the steps prove.
3. **Adopt or write.** For each candidate file, propose a mapping, one line per existing test: the step it proves, "kept, new Sxx beside it" (item 5), or "not a step". Ask with `AskUserQuestion`, per file: adopt it (recommended when it maps to at least one step), or write a new file and leave it alone. With no candidate, or when every one is declined, write a new file at the default path or `--out`.
4. **Conventions.** Read the framework's config (`playwright.config.*`, `cypress.config.*`, `jest.config.*`, `vitest.config.*`, `phpunit.xml`), two or three tests closest to the runbook's capability, and the fixtures and helpers they import (login, i18n, factories, test data). For `api`, also read the "API scripts" section of the agents block. Follow them. When tests read UI text from message files, read expected text the same way instead of copying the string.
5. **Write or edit.**
   - `ui`, mocked: one test per step in run order, named `S01 <step title>`, with the Playwright or Cypress equivalent of an assertion for each Expected. With `viewports`, one test per step and viewport, named `S01 <step title> @ <viewport>`, inside a `describe` per viewport that sets the size from the config. A `beforeEach` posts `{ runbook, mode: 'mocked', step }` to `${RUNBOOKS_UPSTREAM_URL}/__runbooks/select`, with the step taken from the test title, and an `afterAll` posts `{ runbook: null, mode: 'live' }` there. Both send `content-type: application/json`, as Playwright `request.post` with `data` and Cypress `cy.request` with an object body do (`upstream.md`, "Scripts"). Each test then navigates to the step's start page. A step that checks a request reads `GET ${RUNBOOKS_UPSTREAM_URL}/__runbooks/state` and asserts on `requests`, finding a GraphQL request by the `operationName` in its `body`, or in an item of a batch `body`. The script takes no screenshots for design, because only a browser run compares a screen with its design. This shape makes mode `test` available. The fixtures are read, never written here; a step with no fixture is a finding for `/runbooks:update`.
   - `ui`, live: the shape of the next two items, with the login the project's helpers provide. The script creates its precondition data through the upstream API, appends the run suffix from `RUNBOOKS_RUN_ID` to what it creates, and deletes it in Cleanup. It has one test, so mode `test` is not offered for it. It posts nothing to the upstream server.
   - `ui`, Playwright: one `test.describe('<title>')` with one test that walks the steps in run order, one `test.step('S01 <step title>', ...)` per step, an assertion for each Expected, and the login the project's helpers provide. With `viewports`, one `test.describe('<title> @ <viewport>')` per viewport, each with `test.use({ viewport: { width, height } })` from the config, holding only the steps that run at that viewport.
   - `ui`, Cypress: one `describe('<title>')` with one `it` that walks the steps in run order, a `cy.log('S01 <step title>')` before each step, an assertion for each Expected. With `viewports`, one `it('<viewport>')` per viewport that starts with `cy.viewport(width, height)` and holds only the steps that run at that viewport.
   - `api`: one test per step, its name starting with the step id (`S01 <step title>`, or `test_s01_<title>` / `testS01<Title>` where names cannot have spaces, following the file's style). Each test builds its own state, repeating the parent's call when it builds on it, because isolation stays per test; `Parents:` decide the result, not the order of execution. Assert in the order of "What a step can verify": status and body, then the read-back call, then fakes or the framework's database assertion. The request is the step's `http` block, and the response is asserted from its `json` block by the rules of `format.md`, "Request and response of api steps": every key shown, arrays in order and at their length, and each value in angle brackets by its type or source.
   - With role tracking on, every script repeats per role, in the runbook's `roles` order (`all` is every registered role, `anonymous` included). Take the role list from `node "${CLAUDE_PLUGIN_ROOT}/scripts/runbooks.mjs" roles`. Roles in `Roles:` lines limit a step's tests or blocks. A step that is `not-applicable` for a role (a parent ended `denied`, `hidden` or `read-only` for that role, or is `not-applicable` for it) gets no test or block for that role.
     - `api`: one test per step and role, named `S01 <step title> as <role>` (`S01 <step title> as <role> in <case>` with cases). Each test acts as its role through the helper the agents block names ("API scripts"), and `anonymous` sends no credentials. A role line is asserted as it states it: 403 for a signed-in role and 401 for `anonymous`, with the body it names. `junit` reads the step and the role from the name.
     - `ui`, mocked: one test per step, role and viewport, named `S01 <step title> as <role> @ <viewport>` (no `@ <viewport>` without viewports). The `beforeEach` posts `{ runbook, mode: 'mocked', role, step }`, with the role and step taken from the test title, so the `@<role>` fixtures answer. With cases, the name is `S01 <step title> as <role> in <case> @ <viewport>` and the `beforeEach` posts `{ runbook, mode: 'mocked', role, case, step }`, with the case taken from the title, or for a role that runs once its `dataCase` from `passes <id>` (the first case of `cases`). `junit` reads the step, role and viewport from the name.
     - `ui`, live: one test per role and viewport, named `<title> as <role> @ <viewport>` (no `@ <viewport>` without viewports), holding one `test.step('S01 <step title>', ...)` per step that runs for that role and viewport, as with tracking off. In Cypress, one `it('as <role> @ <viewport>')` per role and viewport, with a `cy.log('S01 <step title>')` before each step. Each test logs in as its role with the role's entry in the config `accounts`, through the project's login helper, and `anonymous` logs in as nobody. A role with no entry gets no test, and a run gives its steps `no-account`. With cases, one test per role, case and viewport, named `<title> as <role> in <case> @ <viewport>`. Mode `test` is still not offered for a live script.
     - With cases, take the passes from `node "${CLAUDE_PLUGIN_ROOT}/scripts/runbooks.mjs" passes <id> --json`: each role's tests repeat per case it runs, and the case goes after the role in the name, ` as <role> in <case>`. A role that runs once has one set of tests with no ` in <case>` part, built on its `dataCase`. Each test builds or selects the record of its case: an `api` test builds it with the factory its Preconditions `Cases:` line names ("API scripts" in the agents block), a mocked `ui` test adds `case` to its select so the `+<case>` fixtures answer, and a live `ui` test creates it through the upstream API with the run suffix. A step whose `Cases:` line leaves a case out gets no test in that case. Each test asserts the role line that applies in its case: the line naming the case, else the role's line with no case. An adopted script with role names and no case gets ` in <case>` added to each test of a role that runs per case, one copy per case, and shows the renames in item 3's mapping.
   - Adopted file: rename each mapped test so it starts with its step id, add the tests for steps that have none, and leave every unmapped test untouched. When a mapped test asserts something other than its step's Expected, show both and ask which is right: the script is edited to match the runbook, or the user runs `/runbooks:update` and this command afterwards.
   - A mapped test that asserts more than its step (other records, other state), or checks through the database what the step reads back through an endpoint, is not renamed or trimmed: it stays untouched and unprefixed, and a new `Sxx` test for the step goes next to it. The project keeps every assertion it had. In item 3's mapping, show it as "kept, new Sxx beside it".
   - Comment line: `Runbook <id> (<runbook path>). Change the runbook first, then /runbooks:to-test <id>.`, in the language's comment syntax. It is the first line of a new file; in an adopted file, it goes right above the first runbook test.
   - Never weaken an assertion so the app passes.
6. **Run once** with `tests.<surface>.command` limited to the script (`{files}` = the script, `{junit}` = `.runbooks/junit/to-test-<id>.xml`), and show the result. For a `mocked` runbook, start the server first with `node "${CLAUDE_PLUGIN_ROOT}/scripts/runbooks.mjs" upstream` in the background, start the app with `upstream.urlEnv` pointing at it, and pass `RUNBOOKS_UPSTREAM_URL` to the command; stop the server afterwards. For `api` and for a `ui` script with one test per step, read it with `node "${CLAUDE_PLUGIN_ROOT}/scripts/runbooks.mjs" junit <id> --file <junit>`, and confirm it lists no step with no test and no test for a missing step. With cases, `junit` also lists each test that fits no pass, with the reason: a missing ` in <case>`, a case the runbook does not run, a role that runs once with a case, or a step that does not run in that case. Fix each name it lists. When it fails, compare with the runbook's last report: a script mistake (selector, timing, import, helper, fixture) gets fixed here; an app failure is a finding to report, not something to code around.
7. **Record.** `scripts:` in the runbook frontmatter lists the adopted and new scripts. A candidate the user declined in item 3 leaves the list.
8. **Leave CI alone.** CI jobs, gates and test allowlists are the project's decision; note any that would need the new file. For a `mocked` script, name the job's extra work: start `node <upstream.serverFile> --fixtures <upstream.fixtures> --port <upstream.port>` (the copy `setup` made), plus `--mode live --target <upstream.baseUrl>` when `upstream.baseUrl` is set, so tests that never select reach the live API through it; start the app with `upstream.urlEnv` set to `http://127.0.0.1:<port>`; set `RUNBOOKS_UPSTREAM_URL`; and run every test suite whose app points at the server with one worker (Playwright `workers: 1` for that project or job; Cypress already runs specs one at a time), because the server holds one state for all of them (`upstream.md`, "Scripts"). When `upstream.serverFile` is empty, say that `/runbooks:setup` copies it. When the config sets `upstream.schema` for an API in another repository, also name the contract job: `runbooks.mjs contract --strict` from a checkout of the plugin pinned to the version in use (`upstream.md`, "Contract").
9. **Report.** Your report follows "The report" in `${CLAUDE_PLUGIN_ROOT}/skills/runbooks/references/agents.md`. List in `files:` the script and the runbook. Put in `summary:`: the script path (new or adopted); for an adopted file, the mapping test → step and the tests left untouched; one line per step with the test that covers it; the divergences settled in item 5 and how; the result of the run in item 6 (with each failing step and its error); the `scripts:` change in the runbook; and the CI files from item 8.

Done when the script exists, has one runbook test per step for `api` and for a `mocked` `ui` runbook (with role tracking on, per step and role, and per case with cases), or one `test.step` or `cy.log` per step for a `live` `ui` runbook (with role tracking on, inside one test per role), ran once with a reported result, the runbook lists it, and `summary:` holds what item 9 lists.
