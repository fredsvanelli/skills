# Fixtures match on a partial payload

ADR 0008 left GraphQL variables as its follow-up, and a page with three tabs showed why. The Clients, Contacts and Search Results tabs all send the query `SearchClients`, with the variables `{ type: 'clients' }`, `{ type: 'contacts' }` and `{ type: null, search: 'Fred' }`. Clients and Contacts go out together when the page opens, in the same step, so a step folder cannot split them. Recording had the same gap: both calls mapped to `post--graphql-SearchClients.json`, and the second overwrote the first. A REST endpoint has the same problem when the difference is in a JSON body. A fixture now names the payload it answers in an optional `request.variables` (a GraphQL fixture, next to `operationName`) or `request.body` (a REST fixture). The request must carry every value the fixture names, and it may carry more, as with `request.query`. This is not the query language ADR 0008 rejected: a fixture holds plain values, with no operators, wildcards or path expressions. Arrays and scalars, `null` included, match only an equal value, because partial arrays need rules for order and duplicates that no page needs. A fixture without a payload still answers any payload, so existing fixtures keep working. Among the fixtures of one folder layer, the one that names more fields wins, counting query keys plus payload leaves. The folder layer still comes first, so a step folder overrides the runbook folder as before. Recording saves the full payload with secrets dropped, and a hash of it goes in the file name, so two calls of one operation no longer share a file. A value that changes on every run, such as a timestamp, makes a recorded fixture stop matching. The next mocked run then gets a 501 and the step is `blocked`, so the failure is never silent. The agent removes that key from the file by hand.

## Considered Options

- Matching on GraphQL variables only, and leaving REST bodies out. Rejected: a POST that carries its input in a JSON body has the same gap, and the same matcher serves both.
- Recording a payload only when two calls of one operation collide. Rejected: a file would change name and content depending on what else the flow sent, so re-recording one step could rewrite another step's file.
- Redaction by documentation only, telling the agent to delete passwords from recorded files. Rejected: a login sends a password, `run --record` logs in once per role, and the files go into git. The server drops `password`, `token` and `secret` keys itself.

## Consequences

- `request.variables` needs `request.operationName`, and `request.body` cannot go with it. `runbooks.mjs fixtures` reports a `variables` or `body` of the wrong shape, and the server skips such a file.
- A payload is partial at every object depth. `{ "filter": { "type": "clients" } }` matches a request that also sends other keys in `filter`.
- A fixture that names `null` needs a request that sends `null`. A request that leaves the key out does not match it.
- Recording drops every key whose name contains `password`, `token` or `secret`, or a name in `upstream.redactBodyKeys`, at any depth. Case does not matter, so `accessToken` is dropped. The 501 body and the `unmatched` entries drop the same keys. Dropping a key makes the saved fixture match more requests.
- Only a fixture with a payload counts as the one the server would serve for a request with a payload. A project recorded before this change gets new files in the runbook folder, and the old fixtures stay until someone removes them.
- An unnamed JSON object body is an anonymous GraphQL operation, and is recorded without `body`, only when its `query` is a string that starts with `{`, `query`, `mutation`, `subscription` or `fragment`. Matching on query text stays out of scope. Any other unnamed JSON object or array is recorded with `body`.
- A payload that is empty after redaction, or an empty object body, is not saved, so the fixture keeps answering any payload.
- The copied server changed, so `list` and `coverage` warn about a copy from an older version until `/runbooks:setup` refreshes it.
